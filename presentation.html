A spare keyboard becomes a
Windows control deck

KeySidekick detaches a specific USB keyboard from the system keyboard stack (via the WinUSB driver), reads its raw HID reports, and routes every key through the active profile — without stealing focus from the app you're working in. A second keyboard becomes a remote control: for AI agents, media players, a DAW, OBS, calls, presentations.

The problem

Windows can't tell one keyboard from another

You want a specific keyboard to control a specific app — without its keys reaching the active window, with no lag, and no risk to your system.

ApproachDistinguishes keyboardsBlocks keysLag / risk
WH_KEYBOARD_LL hookno — no device IDyesblocks the whole system input thread
Raw Input (WM_INPUT)only if hDevice != NULLread-onlynone
Interception (kernel filter)yesyeskernel driver, hibernate lockup risk
WinUSB driver replacementyes — reads the device directlyyes — keys never enter the input queueno lag, no kernel code

The trap: cheap / composite keyboards (keyboard + touchpad) report hDevice == NULL even in Raw Input — you can't tell them apart from the main keyboard. KeySidekick doesn't depend on that at all: we read HID directly through WinUSB.

The solution

WinUSB bypass: keys physically never reach the system

The keyboard interface is switched from hidusb.sys → kbdhid.sys → kbdclass.sys to Microsoft-signed WinUSB.sys — via Zadig. Keys stop entering the Windows input queue entirely, and sidekick.exe reads 8-byte HID reports from an async pipe and dispatches them by profile.

1Spare keyboardMI_00 switched to WinUSB (Zadig, once)
→
2HID reportssidekick.exe reads 8-byte reports from the interrupt-IN pipe
→
3Profileactive mode: basic / targeted, key mappings
→
4ActionSendInput, PostMessage to a window, !switch/!launch/!app, macros

✅ What you get

No LL hook → no system lag. Works even with hDevice == NULL. No kernel filter — only WHQL-signed WinUSB. Survives hibernate/sleep (WinUSB handles ACPI). The main keyboard is never touched.

⚠️ What to know

Until sidekick.exe is running, the dedicated keyboard won't type — that's expected (auto-start is configured in the dashboard in advance). Basic mode marks events as injected — in anti-cheat games use targeted mode or restore the HID driver.

Integration

Local HTTP API (loopback, CSRF-protected)

All operations are available from 127.0.0.1:8765: state, devices, profiles, presets, activity, config export/import. Includes the new POST /api/v1/action/fire endpoint — run an action programmatically, as if a key was pressed.

curl http://127.0.0.1:8765/api/profiles        # list profiles
curl http://127.0.0.1:8765/api/v1/state        # unified snapshot
curl http://127.0.0.1:8765/api/v1/hid          # devices + driver state
curl http://127.0.0.1:8765/api/v1/presets      # pad-template catalog
curl http://127.0.0.1:8765/api/v1/activity     # recent fired actions

TOKEN=$(curl -s http://127.0.0.1:8765/ | grep -o 'CSRF_TOKEN="[^"]*"' | grep -o '"[^"]*"' | tr -d '"')
# fire an action programmatically (Live click-to-fire from outside):
curl -X POST http://127.0.0.1:8765/api/v1/action/fire \
  -H "Content-Type: application/json" -H "X-KeySidekick-Token: $TOKEN" \
  -d '{"action":"{Media_Play_Pause}","usage":42,"profile":""}'
# enable the «REAPER DAW» template:
curl -X POST http://127.0.0.1:8765/api/v1/preset/apply \
  -H "Content-Type: application/json" -H "X-KeySidekick-Token: $TOKEN" \
  -d '{"agentId":"reaper","name":"REAPER pad"}'

🔒 Security

The server listens only on 127.0.0.1, requires the X-KeySidekick-Token CSRF token on mutating requests, and checks the loopback Origin. Not reachable from outside.

💾 Export / import

Base64 config: one button — download keysidekick-config.ini + copy the text to the clipboard. Import validates and atomically rewrites the config.

🔌 SSE + revision

Every mutation bumps stateRevision and sends an SSE event — clients stay in sync without polling. The activity feed also arrives over SSE.

   │  HID reports (8 bytes, interrupt IN)
   ▼
sidekick.exe ── WinUsb_ReadPipe (async)
   │  diff key-down / key-up
   ▼

   │
   ├── basic:      SendInput (re-inject into system input)
   ├── targeted:   PostMessage(WND, WM_KEYDOWN/UP) to the app window
   └── action:     !switch / !toggle / !launch / !app / macro sequences
   │

   └── BumpRevision() → SSE → dashboard re-render

Запасная клавиатура
становится пультом управления Windows

KeySidekick отвязывает конкретную USB-клавиатуру от системной клавиатурной стека (WinUSB-драйвер), читает её сырые HID-отчёты и направляет каждую клавишу по активному профилю — не отнимая фокус у приложения, в котором вы работаете. Вторая клавиатура — это пульт: для AI-агентов, медиаплеера, DAW, OBS, созвонов, презентаций.

Проблема

Windows не даёт отличить одну клавиатуру от другой

Нужно, чтобы конкретная клавиатура управляла конкретным приложением, её нажатия не попадали в активное окно, и всё это — без задержек и без риска для системы.

ПодходРазличает клавиатурыБлокирует нажатияЗадержка / риск
WH_KEYBOARD_LL hookнет — нет ID устройствадаблокирует весь системный поток ввода
Raw Input (WM_INPUT)только если hDevice != NULLread-onlyнет
Interception (kernel filter)дадаkernel-драйвер, риск при hibernate
WinUSB driver replacementда — читаем устройство напрямуюда — клавиши не попадают в input queueнет lag, нет kernel-кода

Ловушка: дешёвые / composite-клавиатуры (клавиатура + тачпад) присылают hDevice == NULL даже в Raw Input — их не отличить от основной. KeySidekick не зависит от этого вообще: мы читаем HID напрямую через WinUSB.

Решение

WinUSB bypass: клавиши физически не доходят до системы

Интерфейс клавиатуры переключается с hidusb.sys → kbdhid.sys → kbdclass.sys на подписанный Microsoft'ом WinUSB.sys — инструментом Zadig. Клавиши перестают входить в очередь ввода Windows вообще, а sidekick.exe читает 8-байтовые HID-отчёты async-пайпа и диспетчеризует их по профилю.

1Запасная клавиатураMI_00 переведена на WinUSB (Zadig, один раз)
→
2HID-отчётыsidekick.exe читает 8-байтовые reports с interrupt-IN pipe
→
3Профильактивный режим: basic / targeted, маппинги клавиш
→
4ДействиеSendInput, PostMessage в окно, !switch/!launch/!app, макро

✅ Что это даёт

Нет LL-хука → нет лага системы. Работает даже при hDevice == NULL. Нет kernel-фильтра — только WHQL-подписанный WinUSB. Переживает hibernate/sleep (WinUSB держит ACPI). Основная клавиатура не затрагивается вообще.

⚠️ Что важно знать

Пока sidekick.exe не запущен, выделенная клавиатура не печатает — это ожидаемо (auto-start настраивается в дашборде заранее). Basic-режим помечает нажатия как инжектированные — в играх с античитом используйте targeted или верните HID-драйвер.

🔒 Безопасность

Сервер слушает только 127.0.0.1, требует CSRF-токен X-KeySidekick-Token на мутирующие запросы и проверяет loopback-Origin. Извне недоступен.

База64-конфиг: одна кнопка — скачивание keysidekick-config.ini + копия текста в буфер обмена. Импорт валидирует и атомарно перезаписывает конфиг.

让备用键盘成为
Windows 控制台

KeySidekick 通过 WinUSB 驱动把指定的 USB 键盘从系统键盘栈中解绑，直接读取它的原始 HID 报告，并按当前配置文件路由每一个按键——完全不会抢占你正在使用的应用的焦点。第二把键盘从此变成遥控器：控制 AI 智能体、媒体播放器、DAW、OBS、视频会议和演示文稿。

问题

Windows 无法区分不同的键盘

你希望某一把键盘专门控制某个应用：按键不会进入活动窗口，没有延迟，也不会给系统带来任何风险。

方案区分键盘拦截按键延迟 / 风险
WH_KEYBOARD_LL hook不能——没有设备 ID可以会阻塞整个系统输入线程
Raw Input (WM_INPUT)仅当 hDevice != NULL只读无
Interception（内核过滤器）可以可以内核驱动，休眠时有风险
WinUSB 驱动替换可以——直接读取设备可以——按键完全不进入输入队列无延迟、无内核代码

陷阱：廉价 / 复合键盘（键盘 + 触摸板）即使在 Raw Input 中也会报告 hDevice == NULL——无法与主键盘区分。KeySidekick 完全不依赖这一点：我们通过 WinUSB 直接读取 HID。

解决方案

WinUSB 旁路：按键物理上不进入系统

键盘接口从 hidusb.sys → kbdhid.sys → kbdclass.sys 切换到微软签名的 WinUSB.sys——通过 Zadig 完成。按键完全不再进入 Windows 输入队列，sidekick.exe 从异步管道读取 8 字节 HID 报告，并按配置文件进行分发。

1备用键盘MI_00 切换到 WinUSB（Zadig，一次即可）
→
2HID 报告sidekick.exe 从 interrupt-IN 管道读取 8 字节报告
→
3配置文件当前模式：basic / targeted，按键映射
→
4动作SendInput、向窗口 PostMessage、!switch/!launch/!app、宏

✅ 你得到什么

没有 LL 钩子 → 没有系统延迟。即使 hDevice == NULL 也能工作。没有内核过滤器——只有 WHQL 签名的 WinUSB。休眠/睡眠后依然正常（WinUSB 原生处理 ACPI）。主键盘完全不受影响。

⚠️ 需要了解

在 sidekick.exe 运行之前，专用键盘不会输入——这是预期行为（可提前在仪表盘中配置自启动）。basic 模式会把按键标记为注入事件——在带反作弊的游戏中请使用 targeted 模式，或恢复 HID 驱动。

功能特性

仪表盘、配置文件、实时更新

所有功能都通过内置 Web 仪表盘（http://127.0.0.1:8765/）管理——无需手工编辑 INI 文件。

🔄 配置文件与模式

创建、重命名、复制、删除。两种模式：basic——像普通键盘一样输入；targeted——后台发送到应用窗口（支持按住、自动重复和释放）。

🎯 多应用路由

在同一个配置文件中，不同按键可以指向不同应用：!app:Spotify:{Media_Play_Pause}——发送给 Spotify，其余按键仍按配置文件执行。

⚡ Live + 点击触发

Live 屏幕显示当前配置文件映射网格和已触发动作的实时流。点击任意单元格或流中的任意条目——动作立即执行，无需实体按键。

⌨️ Typed Action Builder

不再使用浏览器 prompt()——改用模态动作编辑器：Keys/Media/Macros/Switch/Launch/Send-to-app 芯片、实时预览、从运行中的窗口选择。

📦 一键 Pad 模板

+ Pad template 一键创建带 F1–F12 的现成配置文件：AI 智能体、媒体、OBS、会议、PowerPoint、REAPER、DaVinci Resolve、Ableton、Premiere、Lightroom。

🎓 首次运行引导

空仪表盘会给你三条路径：「Pad template」「创建配置文件」「键盘设置」。「Start here」按钮可随时返回选择。

📡 SSE 实时更新

状态通过事件驱动更新（revision + activity），连接中断时每 3 秒回退轮询。重载配置时仪表盘不会卡死。

🧭 设置向导

7 步：从「现在这还是普通键盘」到激活：按键识别、准备（自启动、备用输入）、Zadig 指南、WinUSB 校验、模式选择。

🔧 诊断与帮助

Diagnostics 页面：设备状态、管道、配置、日志。Help/Setup：驱动回滚、无线键盘、反作弊警告。

集成

本地 HTTP API（仅回环，CSRF 保护）

所有操作都可以通过 127.0.0.1:8765 使用：状态、设备、配置文件、预设、活动记录、配置导出/导入。包含新的 POST /api/v1/action/fire 端点——以编程方式执行动作，就像按下按键一样。

curl http://127.0.0.1:8765/api/profiles        # 配置文件列表
curl http://127.0.0.1:8765/api/v1/state        # 统一状态快照
curl http://127.0.0.1:8765/api/v1/hid          # 设备 + 驱动状态
curl http://127.0.0.1:8765/api/v1/presets      # Pad 模板目录
curl http://127.0.0.1:8765/api/v1/activity     # 最近触发的动作

TOKEN=$(curl -s http://127.0.0.1:8765/ | grep -o 'CSRF_TOKEN="[^"]*"' | grep -o '"[^"]*"' | tr -d '"')
# 以编程方式执行动作（外部 Live 点击触发）：
curl -X POST http://127.0.0.1:8765/api/v1/action/fire \
  -H "Content-Type: application/json" -H "X-KeySidekick-Token: $TOKEN" \
  -d '{"action":"{Media_Play_Pause}","usage":42,"profile":""}'
# 启用「REAPER DAW」模板：
curl -X POST http://127.0.0.1:8765/api/v1/preset/apply \
  -H "Content-Type: application/json" -H "X-KeySidekick-Token: $TOKEN" \
  -d '{"agentId":"reaper","name":"REAPER pad"}'

🔒 安全性

服务器只监听 127.0.0.1，变更请求需要 CSRF 令牌 X-KeySidekick-Token，并校验 loopback Origin。外部无法访问。

💾 导出 / 导入

Base64 配置：一键下载 keysidekick-config.ini，同时把文本复制到剪贴板。导入会先校验再原子化重写配置。

🔌 SSE + revision

每次变更都会提升 stateRevision 并发送 SSE 事件——客户端无需轮询即可保持同步。活动流同样通过 SSE 推送。

架构

仓库里有什么

🧠 src/sidekick.cpp

约 5k 行：WinUSB 管道、异步 HID 读取、按键差分、按配置文件分发、基于 WS2_32 的 HTTP 服务器、SSE、SSE 令牌、托盘、写操作主线程编组（WM_DASH_OP）。

🌐 web/ 仪表盘

单个 HTML 页面：app.js（仪表盘 + 引导 + Live + 预设向导 + 动作编辑器）+ styles.css。通过 PowerShell 打包进 dashboard_embedded.generated.h。

🧪 tests/

14 个单元测试（config bridge、domain、windows_targets）+ http_integration_tests.sh——53 项真实 API 检查：创建配置文件、映射、预设、fire-action、导出/导入、设备。

数据流

备用键盘（WinUSB）
   │  HID 报告（8 字节，interrupt IN）
   ▼
sidekick.exe ── WinUsb_ReadPipe (async)
   │  diff key-down / key-up
   ▼
当前配置文件（basic / targeted）
   │
   ├── basic:      SendInput（重新注入系统输入）
   ├── targeted:   PostMessage(WND, WM_KEYDOWN/UP) 到应用窗口
   └── action:     !switch / !toggle / !launch / !app / 宏序列
   │
   ├── 活动环形缓冲（上限 24）→ SSE → 仪表盘 Live 流
   └── BumpRevision() → SSE → 仪表盘重绘
构建与测试

快速开始

🏗️ 构建（MinGW-w64）

cd src
build.bat
# g++ -O2 -o sidekick.exe sidekick.cpp
#   -lsetupapi -lwinusb -luser32 -lws2_32 -lshell32 -lgdi32 -static
# g++ -O2 -o probe_device.exe probe_device.cpp ...

只需要 MinGW g++；无需 Windows SDK 路径——WinUSB/setupapi 头文件已随 MinGW 提供。--check-dashboard 会在构建时校验内嵌仪表盘是否最新。

🧪 测试

cd tests
run_all_tests.sh            # 单元测试（13）+ 配置往返
# 集成：先运行 sidekick.exe，然后
http_integration_tests.sh   # 53 项真实 API 检查

单元测试覆盖配置 v3（解析/序列化）、domain bridge、windows_targets 解析器。集成测试针对真实 HTTP 服务器：配置文件增删改查、按键、预设、fire-action、导出/导入、诊断。

🚀 首次运行

copy src\config.example.ini src\config.ini
# DeviceVIDPID=vid_xxxx&pid_yyyy  — 你的设备
cd src
run.bat

然后：仪表盘 http://127.0.0.1:8765/ →「+ Setup keyboard」（Zadig 向导）→「+ Pad template」或手动创建配置文件。
